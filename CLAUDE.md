# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Quickstart repository: `docker compose up -d` runs the whole ShopBite stack locally (Shopware + plugin, demo menu, storefront, Mailpit). It is the entry point linked from `/docs/intro` on shopbite.de, so keep it working with zero configuration.

## Development hub

Sessions for any ShopBite work start here. The other `shopbite-de` repos are cloned next to this one (see the README table); work in them is delegated to an agent in that repo with the `delegate` skill, verified end to end with this stack and reviewed by a fresh agent with the `self-review` skill.

## Pieces

- `compose.yaml`: database, valkey, `init` (Shopware Deployment Helper), `shopware` (:8000, also publishes :3000), `worker`, `scheduler`, `setup`, `storefront`, `mailpit` (:8025).
- `storefront` uses `network_mode: service:shopware`, so `http://localhost:8000` is Shopware on the storefront's server (`NUXT_SHOPWARE_ENDPOINT`, storefront 3.0 and newer read endpoint and access key on the server only) and in the browser (media URLs); ports are therefore fixed. Setup writes the access key as `NUXT_SHOPWARE_ACCESS_TOKEN`; storefront images before 3.0 need the 2.x names `NUXT_PUBLIC_SHOPWARE_ENDPOINT` / `NUXT_PUBLIC_SHOPWARE_ACCESS_TOKEN` instead.
- `setup/setup.py` (stdlib Python, `python:3.14-alpine`): creates the sales channel "ShopBite" (storefront type, because Shopware generates no SEO URLs for headless channels) with two free shipping methods, "Lieferung" (default, `shopbite_delivery`) and "Abholung" (`shopbite_pickup`), each with the plugin custom field `shopbite_fulfillment` (delivery|pickup) and its own lead time, which is the method's Shopware delivery time: "30 Minuten" and "15 Minuten" (unit `minute`, min = max; an existing minute delivery time of that value is reused, else one with a uuid5 id is created). Plugin newer than 1.11.0 and storefront newer than 2.5.0 use them; older releases use 30 minutes for both. Shopware's "Standard" stays unassigned, opening hours 00:00 to 23:59 (no delivery order is possible in the last half hour before midnight, no pickup order in the last quarter hour: storefront and plugin take an order only while now plus the lead time of the selected method is within today's hours, the plugin with 5 minutes of grace, shop time zone Europe/Berlin; `24:00` does not help, the plugin still closes 25 minutes earlier and the storefront's delivery time picker cannot handle it, so open around the clock needs a change in both layers; smoke and hardening tests fail in that window), seeds `setup/menu.json` + `setup/images/<number>.webp`, and writes `/config/storefront.env` (access key, country id, menu category id) that the storefront entrypoint sources. IDs are uuid5 values, so runs are idempotent; it seeds only once so Admin edits survive restarts. Sync calls index synchronously only up to 50 products per request (Shopware queues the rest for the worker), so setup writes products in batches of at most 50, each dish with its variants and cross-sellings (`product_batches()`); then SEO URLs exist before the storefront starts.
- Footer column must not be named "Speisekarte": its link categories would take the SEO paths `Speisekarte/<Section>/` of the real menu sections.
- The storefront seals its session cookie with `NUXT_VISITOR_SESSION_PASSWORD` (layer 2.7 and newer refuse to start without it in production): `compose.yaml` passes `STOREFRONT_SESSION_PASSWORD` or a public demo value; older layers ignore it.
- `storefront/`: the user's storefront, a Nuxt project extending `@shopbite-de/storefront` (content, colours, logo, address). The prebuilt image `shopbite-storefront` is built from this folder, and `docker compose up -d --build storefront` builds local changes (`pull_policy: missing` + `build`). `pnpm dev` runs on :3001 with `storefront/.env`, which the setup service writes (the sales channel has domains :3000 and :3001). No lockfile committed: local builds take the newest layer 3.x, CI passes the exact resolved release as build arg `STOREFRONT_VERSION`. The contact form is on (`shopBite.feature.contactForm`); setup sets `core.basicInformation.email` to info@example.com so contact and order mails have a sender and recipient. Keep its texts neutral (Musterstadt placeholders), never real restaurant data.
- `shopware/Dockerfile`: builds `shopbite-de/shopware` (named build context `shopware`) with `shopware/filesystem.yaml` replacing the S3 config, so files live on local volumes.
- `.github/workflows/images.yaml`: builds `ghcr.io/shopbite-de/shopbite-shopware` (shopware main) and `ghcr.io/shopbite-de/shopbite-storefront` (`storefront/` folder) for amd64 + arm64 on push to main, weekly and on demand (PRs get no checks: run smoke and hardening locally before merging). Images are pushed as `candidate`, the smoke test runs the whole stack with them, and only then `latest` + `YYYYMMDD` move. A change that breaks the smoke test therefore blocks the release. After a merge, watch the run (`gh run list --workflow images.yaml -L1`, `gh run watch`): a red smoke keeps `latest` on the old images; its stack log is the `smoke-test` artifact (`compose.log`).
- `test/smoke.mjs`: Playwright end-to-end test against the running stack (start page, every menu section lists dishes via `/api/listing/<id>`, menu section, pizza with an extra, guest checkout with the preselected delivery and its time field, contact form, both mails in Mailpit; the pickup order is in the hardening test). It matches German UI texts, SEO paths (`/Speisekarte/Pizza/`, `/bestellung/kasse`) and the storefront route answers it reads, so update it together with storefront text, menu or route changes. CI runs it against the released layer, but the next release is storefront main: a check that reads a route must pass against both (e.g. `listing.dishes ?? listing.elements`). A test waits for the answer of a cart write before it leaves the page with `page.goto` (smoke and hardening wait for the response of `/api/cart/lines`): a page view gives a new visitor no session, the first write's answer sets the cookie, and an aborted answer leaves the cart in a session the browser never gets. Shopware limits the contact form per client (3 per 30 s), so runs back to back fail there with 429: wait 30 s between runs. Env: `STOREFRONT_URL`, `MAILPIT_URL`, `SMOKE_SCREENSHOTS=<dir>`.
- `test/hardening.mjs` (`npm run hardening`): end-to-end checks of the plugin and storefront hardening, same style as the smoke test, every check prints ok/FAIL/skip. Plugin: dish line items get label and payload (`productNumber`, `without`) from the products (UI order with a removed ingredient and a quantity change, forged Store API request), orders are blocked while ordering is paused, on a holiday and after the opening hours, a staff user bound to another sales channel sees no ShopBite orders, gets 403 on its settings and on `sales_channel.orders`. Storefront: security headers and `private, no-store` on HTML, generic autocomplete errors, 400 for an unknown listing `order`, `hash` removed from the reset and confirmation URLs. Lead times: the config route lists both methods with fulfillment and minutes (no `deliveryTime`), the methods' delivery times are minute based with these values, the settings route PATCHes `leadTimes` of one method (it then has a minute delivery time of that value, fulfillment kept, 400 for a foreign method; the original delivery time is restored and the created one deleted), the ordering window follows the selected method (closing in 20 minutes: pickup ordered, delivery refused), and the checkout shows "Wunschabholzeit"/"Wunschlieferzeit" with now plus 15/30 minutes as earliest time and stores a pickup order with the comment "Wunschabholzeit: HH:MM". It changes settings, hours, lead times and users through the Admin API and restores them in `finally`. Version gate: plugin checks run when the installed plugin is newer than 1.10.1 (Admin API), storefront checks when `STOREFRONT_LAYER_VERSION` is unset or newer than 2.4.0, lead time checks when the plugin is newer than 1.11.0 (and for the checkout check the storefront newer than 2.5.0); `HARDENING_FORCE=1` runs all (to see them fail on old images). `test/compose.hardening.yaml` gives the storefront a dummy Geoapify key (`HARDENING_GEOAPIFY_KEY=hardening-dummy-key`); the checks never trigger a lookup. CI runs it after the smoke test. Not covered: passkeys and backoffice flows (no backoffice in this stack), real Geoapify lookups.
- `compose.build.yaml`: builds the Shopware image from the Git repository instead of pulling.

## Verify a change

```bash
docker compose down -v && docker compose up -d && docker compose logs -f setup
```

Then order a pizza as a guest on http://localhost:3000 and check the mail on http://localhost:8025, or run the smoke test against the running stack:

```bash
cd test && npm ci && npx playwright install chromium && npm run smoke
```

and the hardening test, with the storefront restarted on a dummy Geoapify key:

```bash
docker compose -f compose.yaml -f test/compose.hardening.yaml up -d --no-deps storefront
cd test && HARDENING_GEOAPIFY_KEY=hardening-dummy-key npm run hardening
```

Test locally built images with `SHOPWARE_IMAGE` / `STOREFRONT_IMAGE` (see `.env.example`, also `ADMIN_PASSWORD`, `SEED_DEMO_MENU`).
